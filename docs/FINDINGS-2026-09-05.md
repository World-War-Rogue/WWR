\# Chat translation: delivery, quality, classification



Written 2026-09-05, after the deploy of c7549677. Found by reading live data

with a signed-in account, not by testing.



\## What was observed



GrandpaWhale posts in Korean. His messages render to an English reader as raw

Korean, with no translation and no tag. The German-tagged message immediately

above them renders in English, so nothing about the feature is obviously broken.



Three Korean messages were checked against the database. All three had

messages.lang correctly set to ko, and all three had an en row present in

message\_translations.



The classifier was right and the translator ran. Every translation exists,

in English, in the database. The client is never told.



Two of those three messages are the tester reporting this bug, in Korean,

through the channel that is broken — which is why it was never seen. He also

found the workaround on his own: close the chat panel and reopen it.



\## Bug 1 — a translation that lands after delivery is never delivered



Chat polls on a since cursor, so each message is sent to a client exactly

once. Translation is written after the message row. If the poll that carries a

message runs before its translation is written, the client holds the

untranslated copy permanently: the cursor has already moved past it and nothing

re-sends it. Closing and reopening the panel refetches from scratch, which is

exactly the workaround the tester described.



This is a race, not a missing feature. The cursor guarantees the loser of that

race never gets a second chance.



\### Fix: an overlap window



The poll returns messages newer than the cursor plus everything from the last

60 seconds, and the client upserts by id instead of appending.



Chosen over the alternatives because it needs no migration, no new endpoint and

no new client state, and because it matches the idiom the rest of the system

already uses: settle on read, and let a later read correct an earlier one.



The two rejected options, recorded so they are not re-derived:



\- Client-driven refetch. Client tracks messages whose lang differs from

&#x20; the reader's and that arrived with no translation, then asks for those ids.

&#x20; Cheaper on the wire, but adds client state and a second code path.

\- A translations cursor. Cleanest conceptually — poll returns translations

&#x20; created since a cursor — but message\_translations has no timestamp column,

&#x20; so it needs a migration. Worth doing if the overlap window proves too coarse.



\### Implementation notes



\- Cursor still advances to the newest created\_at. The window is a floor on

&#x20; what is returned, not a change to the cursor.

\- The client must upsert, not append. Re-delivery of an id already held

&#x20; replaces its body and translation in place.

\- Re-delivery must not re-fire side effects. Unread badges, mention

&#x20; notifications and jump-to-message all key off arrival today; they need to key

&#x20; off first arrival instead. This is the part most likely to be missed, because

&#x20; it will look correct until a re-delivered mention pings someone twice.

\- 60 seconds is a guess at the translation tail. If translations routinely take

&#x20; longer, the window silently stops helping — so it is worth logging the gap

&#x20; between messages.created\_at and translation write for a few days before

&#x20; fixing the number.

\- Show a pending state. Whatever the window is, some message will fall

&#x20; outside it. A message from a language the reader does not read, with no

&#x20; translation yet, should say so rather than presenting untranslated text as

&#x20; final. That single change would have surfaced this bug on day one.



\### Acceptance test



From a second account set to Korean, post to Server. On the English client, with

the panel left open and untouched, the English text appears within the window.

No unread badge fires twice. Then confirm the same for a message that is

mentioned.



\## Bug 2 — the translations are wrong in a way that reads as fluent



Separate from delivery, and worse, because it is invisible.



\- "It doesn't translate right away." came back as "No direct translation."

\- "You have to turn the chat off and on again for it to translate." came back as

&#x20; "Open the chat and translate it again."

\- "Hurry up and give me resources!" came back as "Give me a resource!"



The third is fine. The first two are wrong, and both are wrong in fluent English

— nothing about them looks like a failure. Even with delivery fixed, this bug

report would have arrived as a meaningless sentence and been scrolled past.

The report failed twice, independently.



m2m100-1.2b handles a bare imperative and loses anything with a

clause in it. That is a quality ceiling, not a bug, and it matters because

cross-language play is the differentiator the game is built on.



Worth doing before relying on it further: take twenty real messages from the

existing history, translate them, and have a speaker of each language mark them

right or wrong. Twenty is enough to know whether the ceiling is acceptable.

Chat is also the only per-message ongoing cost in the system, so any model

change has a price attached and should be decided with numbers.



\## Bug 3 — the classifier is wrong in both directions



Message 25fc4979 has lang = de and a body that is plainly English ("i need

to create many th..."). It was round-tripped through the translator and rendered

in the translation styling.



Cheap mitigation: discard a translation that comes back near-identical to its

source. Costs nothing, hides this symptom entirely, and is worth doing

regardless because it also catches the model no-oping.



The real fix is classifier reliability, which is its own investigation. Note the

history here — the detector has already been wrong twice, first storing the

author's reading preference instead of the language they typed, then failing on

Spanish function words. This is the third distinct failure of the same

component.



\## Other findings from the same session



No password reset flow exists. The owner locked himself out of MattofWar

and there is no path back through the interface — the Gate has a request-access

link and nothing else. Recovery required copying a password\_hash from a

throwaway signups row in D1. Every approved player is one forgotten password

from the same position, and the only route out runs through someone with

database access. This belongs above the store on the roadmap.



signups stores a working password\_hash before approval. A pending

request-access row carries a live credential for an account nobody has vetted.

Fine while the owner is the only reader; not fine when signups open to

strangers. Same bucket as text filtering.



Nothing invalidates sessions when a password changes. Irrelevant for a

forgotten password, decisive for a compromised one.



A successful access request shows no confirmation. The form empties and

says nothing. A real applicant cannot tell it worked and will submit twice, or

give up. Same screen as the Gate i18n work, so fix them together.



A D1 write returned code: 7403 and a read seconds later succeeded. The

delete had not happened; a retry worked. wrangler prints a loud error, so the

risk is assuming a write landed. Confirm D1 writes with a read.



wrangler d1 execute --file prints only a summary. The verification

SELECT at the end of grant\_shellwarden.sql never displays, so the

"empty table means the callsign did not match" check described in the status

doc does not actually surface. Run the check as a separate --command.

GrandpaWhale already owned shellwarden — granted 02:13 UTC on 2026-09-05 —

which is why the re-run reported 0 rows written.



The Squads button is top left of the world map, not top right as the status

doc says. It opens the squad editor. The marches panel with Recall only appears

when a squad is away, so it remains untested.



\## The defender's countdown



Recorded from the same session, since it was decided in discussion rather than

built.



The clock should not live on the map. A player about to be hit may be in

Customise, Chat or Squads, so a red column warns only those who happen to be

looking at the right screen — that is something you can discover, not a warning.



Put it above the screen router: a thin strip present on every screen,

rendered only when something hostile is inbound, showing the count and the

soonest arrival, expanding on click. This answers the original objection — it is

not the squads panel, it is not about your own squads, and no number goes back

on the map.



Hostile only. Ally reinforcements are also inbound and also not your squads,

and it is tempting to reuse the container. Don't: once the strip can mean "a

friend is helping," it stops being scannable and the one alert channel has been

spent on something that is not an alert.



Two things that follow from existing architecture. The strip takes an absolute

arrival instant and counts down client-side, like every other timer. And it

should hang off the chat poll rather than adding one — 4s open, 25s collapsed is

already tuned against a real cost.



The part worth keeping: the strip hitting zero is exactly when the battle can

be settled, and battles are settled by whoever looks next. Today a defender

who is not watching the map has no prompt at all and the battle sits unresolved

until someone wanders past. The same component fixes the notification gap and

the settling gap.



Still open, and a design call rather than a technical one: whether the

attacker knows the defender can see the clock. Visible incoming timers are the

genre norm and make defence a real decision rather than a coin flip, but they

also mean no attack ever surprises anyone. Settle it before building, because it

decides whether this is a warning system or a scoreboard.
